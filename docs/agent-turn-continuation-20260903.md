# 跨轮任务与验收继承（2026-09-03）

## 修复的问题

原生运行时原先只根据本次输入分类。上一轮要求“修复登录并运行测试”，下一轮输入“照刚才说的做”，会被归为普通回答；模型只回复“已完成。”、没有任何工具回执，也能进入 completed。前一轮的正文缓冲修复只能阻止提前发布，不能阻止这个终态误判。

本次使用持久化的用户请求和任务合同恢复原生验收门槛，不把模型记得上下文当作可靠性保障。

## 具体行为

1. 对“继续”“继续下一步”“照刚才说的做”“照办”等完整短语，继承最近任务的原始要求，包括换行、表格模块、条件、验收项及合同修订记录。
2. 原始任务、来源、工作目录及前一轮编号保存到原有 assistant 根消息的 `turn.request`，不另建第二套任务存储。重建 runtime、重新加载 PersistentSessionStore 后仍可续接。
3. 新轮创建新任务图；只导入合同定义，清空旧 evidence。上一轮通过的测试、权限确认和重放权限不导入。补上本轮原生回执后仍可正常交付；不得通过删除旧验收项绕过门槛。
4. 模型若只说“已完成”，原任务要求的修改/测试仍是未完成，不再因短句被降为普通问答而放行。原始任务上下文纳入指令去重与丢失后补发，不逐条重复固定指令。
5. OttoServer 显式传入原始用户消息 ID，区分真正的用户要求与额外拼接的企业知识检索上下文；检索资料不再参与本轮原生任务分类或被续接为任务。
6. 换话题、完整的新要求不继承旧任务；不跨越较新的用户消息复活旧目标。明确取消的任务不会因泛泛的“继续”重新执行。
7. 来源/目录变化、任务缺失或过长、合同损坏、后台执行或未知结果，先返回具体澄清，不调用模型或工具，也不标记成功。“继续，但不用测试”等变更不会静默降低原验收标准。
8. 部署、发送、破坏性操作、企业写入，以及裸“同意/授权”等不依靠泛化续接执行。原有恢复记录核对、策略、确认、审计闸门保留。

## 尚未解决的边界

- 这是保守的短句续接，不是完整的语义目标更新器；带条件的复杂改需求仍需澄清。新任务的原始复杂度/意图分类仍有规则边界。
- 旧会话可以回溯实际用户文字，但不能恢复从未保存的验收细项或目录身份。原生记录不足时不凭模型建议臆造合同。
- 暂不自动复用跨轮成功执行状态。特别是“旧轮已经改好文件、新轮只差复验”的场景，仍需进一步实现基于文件状态和新证据的已完成工作复用；不能用复制 completed 节点或重放旧写操作替代。这一步没有解决所有重复劳动。
- 通过用例绑定仍不证明用例的语义充分性；所有上述测试都是确定性回归，固定真实模型的前后基线仍待单独执行。
