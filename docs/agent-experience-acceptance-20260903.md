# Otto 回答与执行体验改进（2026-09-03）

本轮只修改本地代码，不推送、不部署生产、不使用用户模型密钥。保留此前的原生执行回执、逐项验证、任务图交付闸门修复，以及同一工作区的其他企业功能改动。

## 验收与安全规则

- 程序验收必须匹配指定命令、工作目录和实际原生退出回执，退出码为 0；后续写入或同目标后续失败会让旧证据失效。模型声称“完成”、测试名称里带 `test`、无回执的成功字样均不算证明。
- 资料观察必须指向实际返回的工具结果和原文片段；这只能证明来源被观察，不能证明结论必然正确。人工验收项不会被模型自动置为通过。
- 原生计划修改采用版本检查、限制规模、禁止循环依赖与验收 ID 歧义。恢复时不把保存的“已通过”声明恢复成可复用的执行证明。
- 内部计划工具不会作为用户工具卡展示；不新增“直接回答、工具辅助、计划执行”等路由标签。
- 后台 `commentary` 不触发“对话已完成”通知；最终交付才提醒，避免每轮工具进展重复弹窗。无 phase 的旧服务端帧维持兼容行为。
- PPTX 不解包写盘，不执行宏/OLE/脚本，不加载外部关系或嵌入 SVG；拒绝 DTD/实体。限制压缩文件 32 MiB、80 页、XML 单项 2 MiB、图片单项 4 MiB、累计实际解压内容 40 MiB。固定 `@xmldom/xmldom@0.8.15` 和 `jszip@3.10.1`，锁文件保留官方哈希，不附带无关依赖升级。

## 真实模型评测入口

在专用进程/测试账号中运行。密钥只通过进程环境或凭据注入提供，不写配置文件、源码、日志或报告。

显式设置以下环境变量后，从仓库根目录执行 `npm run eval:live`：

- `OTTO_LIVE_EVAL=1`
- `OTTO_EVAL_BASE_URL`：OpenAI 兼容模型接口，必须 HTTPS，或回环地址 HTTP。
- `OTTO_EVAL_API_KEY`、`OTTO_EVAL_MODEL`：专用评测凭据和模型 ID；不读取已有用户凭据。
- `OTTO_EVAL_CASES`：1–6，默认 1。六个案例依次为金额汇总、版本记录选择、缺失证据处理、提示注入数据、部门关联、重复冲突。
- 可选 `OTTO_EVAL_INPUT_PER_MILLION` / `OTTO_EVAL_OUTPUT_PER_MILLION`：每百万 token 单价，单位自行保持一致；估算不含缓存优惠，不能代替账单。

默认不开启时跳过真实调用。每例最多 10 个模型轮次，150 秒时请求取消（提供方不响应取消时可能延迟结束）；仍应设置提供方账单上限。临时目录只含合成数据、结果和独立测试，保留供复核；模型只能读 `input.json` / `result.json`、写 `result.json`，只能执行固定的 `node --test acceptance.test.cjs`，不能读写验收程序或执行自写脚本。

评测临时切换 `OTTO_USER_DIR` 到一次性 profile，结束后恢复；关闭 MCP 发现、环境上下文和遥测，不把合成结果写入工作习惯记录。只允许串行案例。报告写入 `packages/evals/artifacts/live/`；失败请求进入分母，未知 usage/价格/费用为 `null`，不按零成本统计。

离线测试中的 `live-harness-smoke.scenario.test.ts` 通过回环模拟接口运行完整链路（计划、读取、写入、独立 Node 验收、证据绑定、交付）。它不是一个真实模型样本，不能并入真实模型质量分数。

## 验证与后续验收

新增正反向回归覆盖：跨轮/跨会话消息隔离、最终消息不被迟到进展覆盖、计划缺项/循环/版本冲突/串项、伪造证据、写入后证据过期、模型声明不能替代验收、压缩后目标替代与约束保留、PPTX 外链/实体/膨胀包拒绝，以及无预览图与多 PPT 目录的应用预览 API。

本地验证结果：

- core/server 编译通过；core、server、evals 类型检查和 desktop 主进程/预加载/渲染层类型检查通过。本轮改动文件的 ESLint、`git diff --check` 和 code map 校验通过。
- 压缩回归 39 项通过；桌面相关回归 101 项通过，随后新增后台通知用例后消息 store 整组 60 项通过（原为 59 项，即覆盖的桌面相关用例合计 102 项）。
- 确定性场景与回环执行 smoke：5 个文件、7 项测试通过。默认 live 入口跳过，不产生真实模型费用。
- 服务端全量：250 个测试文件，1,856 项通过、2 项跳过、1 项失败。失败在 `packages/server/src/enterprise/server.test.ts` 的“登记 MLS 清理和通知投递，并在服务关闭时全部停止”：同工作区另外的政策情报功能新增 `enterprise.policy-intelligence.collection`，原断言仍只期待 5 个任务，实际为 6 个。未修改那部分功能或放宽断言，也不能把全量结果报告为全绿。

尚未进行真实模型批量质量评测、生产用户试用、任意 Office 版式兼容性验收或安装包发布；不能据此声称达到 Codex/Grok 的成功率、时延或成本。

建议下一步使用团队批准的评测模型和预算，对真实但脱敏的企业任务扩充数据集，固定模型版本与数据版本，分别复核正确性、权限违例、引用准确率、重规划成功率、成本和延迟分布，再决定上线。
