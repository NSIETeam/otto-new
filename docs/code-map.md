## Resident work, scheduling, and RPA

```mermaid
flowchart LR
  Intent[User enables resident task] --> Registry[Recurring task registry]
  Registry --> Fingerprint[Input version / change fingerprint]
  Fingerprint -->|unchanged| Skip[Skip without paid call]
  Fingerprint -->|changed| Gate[Permission + cost + background policy]
  Gate --> Scheduler[Workflow scheduler]
  Scheduler --> RPA[RPA / computer control]
  Scheduler --> Channel[Feishu / WeCom notification]
  RPA --> Audit[Origin, token, provider, retry, cost audit]
  Channel --> Audit
  Audit --> Status[User-visible status and stop control]
```

Primary registration points:

- Desktop lifecycle and local recurring work: `packages/desktop/src/main/index.ts`
- Server-side recurring registry: `packages/server/src/server.ts`
- Generic scheduling state: `packages/workflow`
- Computer automation primitives: `packages/rpa`

## Customer module path

```mermaid
flowchart LR
  Wizard[Desktop module wizard] --> Quarantine[Server quarantine]
  Quarantine --> Scan[Manifest, hash, WASM and permission scans]
  Scan --> Review[Human review]
  Review --> Sign[Platform signature]
  Sign --> Registry[Installed module registry]
  Registry --> Host[Versioned customer-module Host ABI]
  Host --> Policy[Confirmation, policy, audit, cost, idempotency]
  Policy --> Events[Declarative UI and typed result events]
```

Customer modules stay outside the runtime kernel. Desktop owns declarative presentation and activation; Server owns review and distribution; the Host ABI exposes only controlled capabilities.
