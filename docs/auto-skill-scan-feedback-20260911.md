# “立即分析”没有反馈修复

## 原因

Skill 草稿弹窗的按钮会发送 `scan_pending_auto_skills`，但此前没有任何分析等待状态、完成提示或超时处理。空扫描与初始空列表渲染相同；`auto_skill_failed` 只进入共享工作区 error，没有传入此弹窗。较窄弹窗还会把“立即分析”挤成两行。

## 本次修改

- 点击立即显示“分析中…”及说明，禁用重复点击；不再将 void 发帧当作异步操作已经完成。
- 增加扫描专用 requestId 与完成回执，普通列表读取、后台刷新、旧请求回执不会结束当前扫描。旧客户端的空 payload 仍兼容。
- 完成时显示实际候选数量；空结果明确显示“未发现符合条件的新候选”，并提示积累实际成果或主动创建 Skill。
- 服务报错显示在当前弹窗，不被日程等其他消息清除。离线和发送失败直接解释；120 秒无回执或运行中断线标记结果未知，不自动重发、不宣称取消。迟到的匹配回执仍能恢复结果。
- 服务器对仍在执行的手动扫描复用同一个 Promise，避免用户重复操作再次发起相同工作。此处不是跨进程、跨重启的幂等任务系统。
- 扫描进行中或结果未知时不允许确认/拒绝旧候选，避免与在途暂存发生竞争；结束后仍需用户另行确认安装，不自动执行草稿。
- 工具栏允许说明换行，按钮不收缩，文字保持单行。

## 验证与边界

界面、状态及 App 接线回归 58 项通过，服务端协议和 HTTP/WS 测试 127 项通过。其中真实本地 HTTP/WS 测试覆盖空扫描回执、实际暂存 IO 失败及在途操作复用；并发测试只控制在途 Promise，不伪称进行了付费模型评测。类型检查、lint、生产 renderer 构建和代码地图检查通过。

仍保留扫描器原有的日志规则预筛与模型失败模板回退；“扫描完成”只说明候选扫描结束，不代表每次都调用了模型，更不代表候选业务效果已验证。本次没有重新实现候选生成质量评测，也没有调用真实用户日志或付费模型。

仅修改本地源码/构建，没有推送、发布、替换正在运行的安装版或操作线上服务器。新 UI 与本地 server 的回执扩展需要随同一构建交付；旧 server 缺少回执时不能假报完成，会提示核对配套版本。doctor 的既有 Windows npm.cmd 探针失败未纳入“全部通过”。
