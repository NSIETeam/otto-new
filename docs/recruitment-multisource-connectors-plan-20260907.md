# Otto 多渠道招聘来源中心实施规划

> 2026-09-08 补充：[来源材料闭环及验收边界](recruitment-source-material-closure-20260908.md)。检索结果已接入当前客户端候选人分析工作区；完整档案服务端共享和真实平台验收仍未完成。

## 目标

把智能招聘从“用户上传一份材料后分析”扩展为“从多个经过授权的来源持续发现、导入和更新候选人”，同时保证每条信息可追溯、候选人个人信息受到保护，任何对外联系均由招聘人员确认。

## 产品边界

- Otto 可以自动调用已连接且具备约定工具的招聘 MCP/API。
- Otto 不保存招聘网站账号密码，不绕过验证码，不模拟真人浏览，也不抓取未授权页面。
- 平台没有开放接口时，只提供人工导入、候选人自主投递或企业商务接入提示。
- 候选人搜索、详情读取与状态同步属于只读自动化；发布岗位、联系候选人和安排面试属于外部写操作，必须经过确认、幂等和审计。
- 模型只负责材料理解、证据整理和建议，不自动作出录用或淘汰决定。

## 第一阶段：可信来源层

1. 建立来源目录，覆盖手动导入、企业人才库、员工推荐、招聘邮箱、投递页以及主流招聘平台。
2. 定义招聘 MCP v1 工具约定：
   - 必需：`search_candidates`、`get_candidate`
   - 可选：`sync_candidates`、`draft_outreach`、`send_outreach`、`publish_job`、`schedule_interview`
3. 只有 MCP 已连接且两个必需工具都存在时，界面才显示“可以自动寻才”。
4. 给候选人档案增加来源记录，包括渠道、来源记录编号、导入方式、授权状态、发现时间和原始文件名。
5. 在智能招聘工作台增加“候选人来源”面板，展示真实连接能力和下一步操作。

## 第二阶段：企业服务端来源网关

1. 将候选人档案、来源记录和同步游标放到企业服务端，按企业、岗位和招聘人员隔离。
2. 对多个连接器并发搜索，单个渠道失败不影响其他渠道；界面分别显示结果数、耗时和错误。
3. 使用经过哈希的邮箱/手机号以及人工复核信号进行去重，不用姓名相似直接自动合并。
4. 字段冲突并列保存来源与时间，不静默覆盖较早材料。
5. 后台同步仅在管理员开启后运行；没有变化时不调用大模型。

## 第三阶段：招聘闭环

1. Otto 根据岗位画像生成各渠道搜索计划并持续补充候选人。
2. 为候选人生成个性化沟通草稿；招聘人员可以逐条或小批量确认发送。
3. 回复、面试安排和招聘阶段回流同一候选人档案。
4. 提供来源效果分析：有效候选人率、回复率、面试率、人工时间和渠道成本；禁止把模型分数当成录用概率。

## 首批渠道目录

- 综合招聘：BOSS直聘、智联招聘、前程无忧、猎聘。
- 技术与互联网：拉勾、脉脉招聘、牛客招聘。
- 实习与校招：实习僧、国家大学生就业服务平台（24365）。
- 公共与国企招聘：国聘。
- 国际招聘：LinkedIn、Indeed。
- 企业自有来源：企业人才库、招聘邮箱、员工推荐、候选人投递页和手动上传。

上述平台默认均不宣称存在公开自动化接口；实际能力以企业与平台获得的官方授权、商务合同和当前接口权限为准。

## 第一阶段验收

- 来源面板能区分本地可用、需要配置、等待官方授权和连接异常。
- 未连接平台不会显示为“自动寻才已启用”。
- 伪造相似名称但缺少约定工具的 MCP 不会获得自动搜索能力。
- 手动导入的候选人档案包含来源证据，隐私面板可以查看。
- MCP 的外联工具仅被标记为“需要确认”，不会因为连接成功自动发送消息。

## 当前实现状态（2026-09-07）

- 第一阶段已落地：桌面端来源目录、能力核验、候选人来源证据和对话寻才入口均有测试覆盖。
- 第二阶段内核已落地：企业服务端提供多来源并发网关、来源级超时/错误隔离、哈希身份去重、冲突证据保留、加密 SQLite/PostgreSQL 存储和同步游标。
- 招聘 MCP v1 已提供通用适配器；只接受管理员信任且同时提供 `search_candidates`、`get_candidate` 的连接器。
- 后台变化门已落地：只有管理员开启后才同步；候选人证据指纹没有变化时不会调用大模型。
- 工作台已增加“按当前岗位自动寻才”，请求只允许搜索与详情读取，不会隐式发送消息、发布岗位或安排面试。
- 尚未取得任何招聘平台的正式授权凭据，因此当前代码不会宣称 BOSS、智联等平台已真实自动接入；接入时应由部署方通过服务端公开的招聘来源接口注入官方 API/MCP 适配器。
