## 停止条件与处置顺序

以下任一事件出现，包括尚待核实的可信报告，都立即冻结新任务调度和扩大范围：

- 越权访问或越界操作。
- 重复发送。
- 重复部署。
- 关键错误交付（例如把损坏/错误对象交付为正确结果）。

疑似事件可以先记录，没有完整证据不能成为继续扩大的理由；证据随后补齐。停止记录必须先于耗时的源码/证据校验持久化，因此即使后续校验失败，也不能丢掉停止信号。

处置顺序：

1. 冻结新增账户、企业、客户端分发及新副作用调度；不要只关闭一个 UI 提示。安全可取消的未开始节点取消。
2. 保存事件、任务 ID、候选/模型版本、工具调用和原生回执；先保护证据，不清空日志、队列和恢复记录。
3. 对已经执行中的发送/部署，查询接收端与幂等记录，区分成功、失败和未知。**未知不能自动重放**，停止也不等于撤回已经送达的消息。
4. 负责人按已演练的方案决定回滚受影响测试客户端；有服务端变更时，先冻结测试写入并确认数据/Schema 兼容性，不能直接把旧数据库覆盖回去。
5. 保留故障时点数据，将稳定包启动在明确的测试配置上；必要的数据恢复先在副本验证，再由负责人确认，不能误伤生产数据。
6. 回滚后核验登录、测试企业权限、消息历史/未读、已执行动作是否重复及文件交付；保留回执和前后哈希。未通过仍维持停止。
7. 修复后另开候选/批次，重跑原失败、关键安全与新保留任务。不得因为随后几次测试通过而自动恢复或扩大。

监测不完整也应冻结新调度并核对在途结果。成本/延迟明显增加须保留对照和原因；不得隐藏指标或用解释替代审核。
