# Otto 政策智能服务 PRD v1.3（冲突修订版）

日期：2026-09-03。基于 v1.1 与 v1.2 合并修订；本文件是产品与研发要求，不是对政策效力的法律意见，也不是已上线证明。实现及验收状态见《policy-intelligence-v3-checklist.md》。

## 1. 目标与边界

帮助企业回答：有哪些相关政策；本批次能否申报；哪些条件已有依据、哪些不满足、哪些还不知道；需要准备什么、去哪里核实和申请。

- 面向所有企业，不绑定宏创园区、北京市或昌平区。沿用右侧官方模块及现有对话入口，不新造一套操作入口。
- 默认关闭企业个性化分析，公共政策可浏览。管理员确认后开启，关闭弹窗不等于停用服务；停用后停止本企业后台模型任务。
- 基于原文和企业事实辅助判断，不承诺获批，不自动申报、不代填上传材料、不自动联系第三方。
- 本期重心是有依据的筛查、缺口问答和准备记录，不强行增加向量数据库、多级审批平台或固定三次模型调用。

## 2. 继承与修正

保留 v1.2 的独立排除条款、政策版本与效力治理、金额依据、反馈纠错。保留 v1.1 的资料授权、隐私隔离、原文核验、数值比较、AND/OR 条件、缓存和额度限制。

必须修正的冲突：

1. 地区按企业注册所在地关联国家、省、市、区县；北京、昌平只能作为示例，不能作为产品筛选上限。
2. 类型为可扩展标签而非固定五类。一个政策可以有多类；新增类型不改变诊断协议。
3. 本批次资格与未来准备分开。收入、成立年限等必需条件不满足，当前结论是不满足，不得仍标“潜在符合”。
4. “不知道”不等于“没有”。排除项未知不作硬拒绝；必需事实未知也不能给肯定结论。
5. 排除项必须核验适用对象、例外、条件分支；不能把局部路径排除扩成全局一票否决。
6. 文件效力与申报窗口分开。没有明示有效期显示“效力待核验”，不能默认为现行有效或永久有效。
7. 不把完整企业档案发送给模型。后台只用已授权基础字段，诊断只补充本政策实际需要的字段。
8. 企业反馈是待核实线索，不是官方规则；额度用尽、材料不全、竞争排序等失败不能自动转成资格排除条件。

## 3. 政策来源与更新

### 3.1 地域、类型与覆盖

注册地支持省、市、区县；直辖市不重复展示省级。仅提供模糊区名时要求补充城市，不猜测属地。全国开放不等于已经覆盖全国所有网站：界面必须显示已配置来源与缺口，未收录不能表述为当地没有政策。

默认类型可包括资质认定、人才、项目补贴、税收、政策活动、融资、就业社保、知识产权、绿色低碳、数字化、外贸等，允许新增和多选。原文行业术语与企业描述用语义辅助关联；别名仅帮助发现，不能自动等同资质证书或成立硬条件。未经审核不得编造行业标准代码或固定匹配权重。

### 3.2 来源证据

仅采集明确配置的官方 HTTPS 来源。保留标题、原文链接、来源、采集时间、正文指纹、版本、引用和附件状态。文号仅在原文确实出现时记录，不以虚构文号补齐必填项。

同一 URL 正文变化保存历史正文快照；新批次通常是独立政策，不能简单覆盖旧批次。没有收录到、采集失败、附件未解析、明确废止是不同状态。

来源冲突时核实是否同一文件和批次、发文机关、明确修订/废止关系。不能只凭“级别更高”或“发布时间更晚”自动覆盖；未能证明关系的保留证据并提示待复核。

### 3.3 更新责任

采集在服务器共享执行，客户端启动、退出不逐企业重复爬取。默认北京时间 03:00、18:30 检查新条目；历史已收录正文按有限预算轮询复查，临近截止和已有诊断的条目优先。失败保留上次记录并显示不可用，不能假装更新成功。

模型结构化解读按正文及解析版本缓存，多企业复用；企业分析按企业事实、政策正文和规则版本失效。任务须有集群互斥、超时、额度和可见错误。

跨网页自动追溯所有废止关系、所有地区专用适配器、人工政策审校团队及响应时限，属于后续运营建设，必须单独验收后宣称提供。

## 4. 用户与数据

普通成员浏览公共政策、原文与覆盖情况。管理员维护共享基础资料、开启分析；诊断回答、申报反馈、纠错说明按企业和账号隔离。材料准备状态可由企业管理员共享维护。

基础资料优先复用现有企业档案：注册所在地、行业、成立时间、登记类型、主营业务、资质等。基础资料不足逐项询问；允许“不确定”，不强迫用户猜数。

营收、研发投入、信用状态等敏感字段仅在相关政策诊断需要时询问。默认不共享、不加入企业记忆、不进入模型训练或公共政策库。另勾选共享仅保存明确支持的企业字段。对金额、人数、年度、币种和适用批次必须区分；不具备计算依据时停止自动结论。

## 5. 判断流程

1. 先校验来源、附件、批次时间和已确认的效力变更。
2. 检查独立排除条款：适用范围 → 触发事实 → 例外。事实缺失为“待核实”；明确命中才判不满足。
3. 检查可计算的必需条件及 AND/OR 路径。路径 A 不通过但路径 B 明确通过，不得整体否决。
4. 对仍需语义理解的内容使用模型综合阅读原文与最小必要资料。数值条件由确定性规则复算，模型不得覆盖算术结果。
5. 同一次模型输出包含反向核验：是否漏了条件、引用是否支持结论、事实有无时间口径问题。有疑问就降为待核实，不把模型猜测的“隐性条件”写成硬规则。
6. 一次只问一项缺失事实；允许跳过。重用未变化的诊断，已明确命中排除或硬条件失败时可直接停止，不追加模型费用。

### 5.1 展示结论

- 已有资料支持：核验路径和排除项无未决问题，仍以主管部门审核为准，不叫“保证符合”。
- 待补充／待核实：具体列出未知项，不叫“有申报潜力”。
- 当前不满足：显示本批次差距或命中的排除条款、适用范围、例外与原文。
- 已截止／已废止／已失效／冲突待核实：不能继续输出当前可申报结论。

列表保留“值得评估”“提前准备”“全部政策”。“值得评估”允许相关但待核实的项目，卡片必须显示真实诊断状态；“提前准备”本期仅收录已核验条件、尚未开放的明确批次，不能把必需条件失败包装成可申报。失败、截止、撤销及参考政策仍可从全部列表回看。

### 5.2 金额与资源

展示原文支持内容。只有原文明确的定额，或已核验的比例、基数与封顶值可以确定性估算；资格未明、基数未知、按竞争择优、复杂档位或累计抵扣关系未解析，不输出估算金额。

显示计算式、原文和“估算非获批/到账金额”。补助基数必须是政策认可的合格投入，不将所有企业支出默认视为合格。资源对接只提供原文可核实的官方链接，不编造联系人，也不自行联系。

## 6. 界面与对话

模块卡片展示级别、类型、批次、原文来源、更新时间和资格状态。详情一屏串起“排除核验 → 申报条件 → 诊断摘要与下一问 → 支持依据/估算 → 材料 → 反馈”。

对话可查询相关政策、选择某项开始诊断、回答下一项、查看条件和材料；与模块共用同一服务端记录。例：“看看适合我们公司的政策”“诊断第 1 项”“不确定，先跳过”。涉及启用、共享资料、保存反馈等写操作仍需明确确认。

重要变更不能静默抹掉已准备的工作。旧诊断保留但标记过期，重新核验后使用。模块显示变更提醒；后续接入现有“我的消息”时必须同账号隔离、按政策版本去重，不能另造企业聊天或伪装为工作人员私信。尚未接入消息投递前，不宣称可主动通知离线用户。

## 7. 申报反馈与纠错

管理员可记录已提交、已获批、未通过或判断有误，补充资格/材料/名额/竞争/其他原因。保存前明确确认，允许修订和删除；并发修改校验版本，避免覆盖他人或旧窗口的记录。

纠错记录显示“待核实”，这是线索留存，不代表已联系主管部门、人工已接单或承诺响应时限。正式人工复核接入后，必须展示处理责任人、证据和处理结论；本期不自动修改任何公共规则。

申报成功率仅是有结果的自报样本统计，不叫模型准确率。匹配准确率和误拦截率需要独立复核样本、清晰分母及样本量，不能从用户点击或申报失败直接推算。

## 8. 验收底线

- 外地企业不会被绑定到宏创、北京或昌平；类别可扩展，来源缺口可见。
- 有例外的排除条款、未知事实、AND/OR、多路径、已截止与无有效期，均有正反向测试。
- 当前不满足不出现在“提前准备”中伪装机会；未知项不作确定性排除。
- 资料与政策/规则变化使旧结果失效；原文保留快照，失败可见，不用旧记录冒充新抓取。
- 普通成员及其他企业/账号不能读取本人的诊断回答、反馈；模型只收到实际需要的资料。
- 反馈重复提交、并发修改、删除后旧请求、跨账号伪造均受校验；反馈不改规则。
- 模块和对话的布尔、数字与“不确定”输入口径一致；不新增自动申报或外部联系权限。
- 每项已实现能力给出可复现的检查路径；外部模型、真实云部署和运营覆盖未验收的单列说明。
