# 智能招聘下一阶段：企业共享岗位档案

日期：2026-09-08。工作目录：`D:/otto/otto-push-20260901`；分支：`internal`。

本轮接续“检索结果 → 材料读取 → 全文分析”阶段，新增可实际调用的企业共享存储与岗位授权。不是整套招聘路线已完成，也没有宣称 Workable/Ashby 真实账号已经接通。

同日后续已补跨岗位候选人关联、资料复用和独立进展，详见 [后续验收说明](recruitment-cross-job-candidates-20260908.md)。下方“尚未完成”保留本阶段完成时的状态，以后续说明为准。

## 如何检查

1. 使用支持 `recruitment_jobs_v1` 的企业服务器及本轮 Electron 客户端登录管理员账号。
2. 打开右侧智能招聘，填写岗位目标并导入候选人。展开上方“企业共享岗位”。
3. 确认有权共享材料，点击“保存当前岗位”。应显示“已保存 v1”，继续修改后应显示“有未保存修改”。首次保存仍由管理员创建岗位。
4. 展开“管理当前岗位协作者”，点击“选择企业同事”，勾选本企业 HR/用人负责人并保存授权。
5. 另一已授权账号登录，刷新岗位列表，选择同一岗位，确认替换本地工作台后加载。应看到已有材料、分析及人工记录，不应再次调用模型。对话和右侧模块沿用同一个已加载工作台。
6. 两个客户端加载同一版本后分别修改保存，第二个保存应返回版本冲突，不得覆盖较新的结果。本轮不提供自动冲突合并。
7. 撤销协作者后，其后续加载/保存应被拒绝；其他企业同名岗位互不相通。
8. 清除本地候选人后再次保存，服务器当前副本才同步移除。删除整个共享岗位须由管理员单独确认；本地副本不会一起删除。

保存和加载是用户主动操作，不是后台自动上传。请勿把“本地已分析”理解成“企业已保存”。

## 已实现

- SQLite 与 PostgreSQL 存储实现，并接入两种企业服务器生产入口；不依赖招聘来源连接器是否配置。
- 每个岗位独立保存候选人、已提取正文、来源记录、已产生的语义分析、面试转写、实战文本、人工记录及已有来源版本历史。
- 档案正文与岗位元数据使用现有字段密钥加密，绑定企业、岗位和字段上下文；没有引入明文凭据或单独要求购买 KMS。
- 岗位级授权：管理员管理岗位，分配的 HR/用人负责人可读取和更新；无权限账号不可见岗位内容。
- 原子版本比较更新，避免多人覆盖。删除后仅保留无正文的标识墓碑，阻止迟到的旧创建请求复活档案。
- 服务端从登录账号推导企业与身份，拒绝调用方伪造组织或管理员标记。
- 进入现有企业审计路径，记录保存/授权/删除请求及完成信息；日志不包含简历、手机号、模型输入或访问令牌。正文里的历史用户记录不是服务端签名证据。
- 加载前校验嵌套文档结构、候选人关联与保存期限；无效文档不会覆盖当前工作台。
- 切换账号/服务器时中止旧请求的后续应用；请求固定目标服务器及会话。切换岗位后旧对话结果与确认草稿不能写入新工作台。
- 保存、加载、授权、删除都不需要调用大模型；恢复既有分析不会新增模型 Token 消耗。

## 约束与尚未完成

- 当前是“按岗位保存的共享工作台”，还没有拆成全企业唯一人物实体 + 多岗位投递实体；不会因同名自动合并人选。
- 归档已有提取内容与结果，不包含原始 PDF/Word/音视频文件的二进制托管，也不自动重建尚未产生的历次模型结果。
- 源材料读取/搜索仍沿用原来源网关管理员权限；本轮岗位授权只覆盖共享档案。HR 可接续已归档材料，不代表取得平台人才库搜索权限。
- 每岗位最多 100 位候选人，每份候选人文档最多 100 万字符，请求整体最多 600 万 UTF-8 字节。超过限制明确拒绝，不静默裁剪正文或历史。
- 保存/读取时过滤过期候选人，读取时以原子版本更新清理服务器当前档案。尚无独立后台定时清理；长期未访问的岗位、WAL、备份及导出副本遵循对应运维保留策略，不能宣称到期瞬间物理擦除所有副本。
- 撤销授权会阻止后续服务器访问，但无法收回同事已经读取、截图或导出的资料。
- 审计完成写入若在业务保存后失败，操作结果可能不确定；应重新加载核对，不要创建另一个同名岗位重试。
- 尚未完成真实 Workable/Ashby 授权验收、招聘邮箱/投递页/推荐入口、持续后台同步、消息发送及 ATS 双向进度回写。
- PostgreSQL 已做适配器 SQL 合同测试；没有在真实 PostgreSQL 集群上进行并发、故障切换与长期存储验收。新档案表的 SQLite → PostgreSQL 迁移和备份恢复演练应另行验收后使用。
