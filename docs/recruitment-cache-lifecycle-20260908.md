# 智能招聘：临时检索缓存生命周期

日期：2026-09-08。基于上一轮 Workable 运行链路继续完善，不代表整个招聘路线已完成。

## 本轮变化

- 服务器临时检索结果与分页游标保留 24 小时；到期立即不再通过读取接口返回。桌面结果区说明这一期限，过期取材料会提示重新检索。
- SQLite 单机服务器、PostgreSQL 集群服务器使用现有常驻任务注册器清理过期数据库记录。启动注册后安排首次执行，此后每分钟每实例最多删除 500 条；积压分批消化，不同时扫描并删除所有历史数据。
- 本人注销和管理员删除账号，在同一账号删除事务中清除该账号的加密检索快照，同时撤销其 Workable 凭据。旧格式快照无需迁移，按企业分页解密确认归属，不按姓名或岗位猜测所有者。
- 删除中若遇到不可解密记录，事务回滚并返回失败，不声称已清理成功。SQLite 注销墓碑重放也处理“账号已删除但备份仍带旧快照”的情况。
- 账号已注销、停用或不属于目标企业时拒绝新增检索快照。PostgreSQL 新增快照在同一 SQL 中锁定有效账号，与删除账号的行锁串行化；不依赖先查询再写入的时间窗口。
- 简历读取过程中、读取完成后以及审计等待结束后再次检查授权和快照有效性。获取历史搜索结果时，岗位权限检查完成后也重新读取快照，避免返回等待期间已清理的数据。
- 清理任务失败会用不含候选人内容的错误报告并重试；同一实例的慢任务不重叠。关闭时等待已开始的清理批次结束，再释放数据库连接。

## 明确不改变的内容

正式入档的企业共享候选人、岗位、评价和面试材料不由这个临时缓存任务删除，继续遵循其现有保留及岗位权限规则。不会因为一个 HR 离职而删除整个企业的候选人档案。

此处的“清理”是删除在线数据库中的缓存行，不是安全擦除数据库文件空闲页或所有离线备份。历史备份仍受原数据治理保留与恢复流程约束。桌面已显示在内存中的摘要也不是数据库缓存行；到期再次读取材料需要重新检索。

分页游标是无姓名的加密来源位置标识，按同样的 24 小时 TTL 清理；本次按账号注销清理针对可确认所有者的搜索快照，不猜测旧游标的所有者。游标过期后重新从来源获取结果，已有正式档案仍按原去重规则处理。

本轮不增加模型调用、自动搜人、自动分析、对外联系或额外 Token 消耗。没有访问真实候选人或执行生产数据删除。

## 验证和检查入口

本轮累计验证 671 个不同用例：服务端招聘、集群、仓库、权限、身份与数据治理 362 项；企业 HTTP 106 项；桌面招聘及相邻流程 203 项。HTTP 全量首次通过 105 项，另一项为任务清单尚未包含新增维护任务；更新预期后，该项连同常驻任务组共 7 项复测通过，未重复计数。Server TypeScript 构建、桌面三端类型检查、相关 ESLint、Preload/Renderer 生产构建、doctor、代码地图和差异空白检查通过。

- `recruitmentCacheLifecycle.test.ts`：精确到期边界、分批物理删除、跨账号/企业保留、删除后迟到写入拒绝、损坏密文回滚、旧备份墓碑重放。
- `recruitmentCachePostgres.test.ts`：原子账号锁写入、所有读取的 TTL 条件、清理时复核外层更新时间、101 条旧格式加密记录的分页归属清理。使用 SQL 契约替身和隔离 SQLite 数据，不是真实 PostgreSQL 并发验收。
- `recruitmentCacheMaintenance.test.ts`：启动和周期执行、零模型费用、失败重试、安全错误、慢任务不重叠、退出等待。
- 材料及 HTTP 路由回归：读取、审计和岗位权限等待期间失效的结果不再返回。
- 企业真实本机 HTTP 与临时 SQLite 测试：本人注销、管理员删除、保留同事快照及正式共享岗位，以及服务器任务登记与退出。Workable 响应仍使用模拟数据。

## 上线前仍需验证

1. 真实企业 Workable 账号的 OAuth、岗位范围、工具参数和简历附件闭环；模拟通过不等于平台验收。
2. 真实 PostgreSQL 多实例并发下的新增/删除/游标更新/清理竞争、数据库慢查询和退出超时，以及真实存量规模的清理吞吐。
3. 正式候选人档案本身的保留、导出、删除及离线备份治理，不能用临时缓存清理代替。
4. 招聘邮箱、投递页、持续自动同步、第二家 ATS 及候选人邀请仍是后续增量。

本轮仅在本地修改并验证，未推送、未部署，也没有启用 Workable 生产批准。
