## 已实现的行为

1. `taskRequirements.ts` 保留需求原文、稳定 ID、模块与条件，在既有 kind/outcome 上增加四组 category：must_implement、must_preserve、must_not_happen、human_judgment。支持“不要/不得/禁止”及“别打开、不启动”等短约束；引用块、代码围栏不直接升级为操作指令。
2. `turnConstraints.ts` 从本轮真实用户请求建立原生约束记录，包含 turnId、可用时的 sourceMessageId、请求摘要、监控器、文件初始哈希、执行覆盖、拦截记录和人工确认回执。压缩后的模型文字、工具返回内容和 update_task_plan 的自报不能改写它。
3. 明确禁止打开 WPS/外部应用时，在审批前及实际 dispatch 前检查。当前仅放行可核对的内置读写/问答工具；MCP、委派、批处理、通用 shell 等未隔离执行器保守拒绝。还核对原生实现与名称，防止同名替换获得白名单权限。常驻审批/YOLO 或本次工具批准不能覆盖用户禁令。
4. 对“只允许修改当前工作区”“不要越界写入”及反引号指定的工作区内子目录，校验写入目标、相对路径、目录联接、符号链接、硬链接与审批等待后的目标变化。无法解析或与工作区冲突的范围不扩大为整个工作区。
5. 对“保持 `config.json` 不变”一类文件约束，记录初始内容哈希、阻止直接修改，并在交付前重新读取比较。任何指定对象缺失观察，整条约束不能通过。拦截成功与实际执行分开记录。
6. 对“不展示绝对路径”，工具型回答和受该约束的纯文本回答先缓冲，再处理可见正文；中间消息、最终消息、异常、取消及工具卡展示副本均走检查。原始工具回执仍用于验收，不拿展示脱敏后的文字代替证据。保留友好 Markdown 文件链接目的地址，代码块/行内代码里的伪链接不能豁免；网页链接不被误删。
7. 补齐 Desktop 的本地 Markdown 文件链接渲染：`[查看报告](<本地地址>)` 显示友好名称；PPT 点击后走已有应用内预览，不自动调用外部应用。人工验收卡显示待确认内容，按钮为“确认这版交付 / 暂不通过”。
8. 人工判断在本地交互会话中通过原生随机一次性确认 ID 处理，绑定本轮、正文和可观察链接文件的哈希。模型自报、伪造 ID、always_approve、拒绝、过期正文或变更文件都不算通过。此确认不授予工具权限。
9. `taskContract.ts` 支持 constraint 验收类型，仅消费原生证据；业务语义约束（例如保留数据顺序）继续要求对应场景、正反向结果和当前修订的具名测试回执。不能用任意绿色测试替代，也不会把所有业务要求误当作文件操作禁令。
10. `agentTurnTracker` 把约束检查纳入完成判定。覆盖尚未启动、调用尚未结束、已知观察缺口、恢复时缺少完整旧轨迹，均不以“日志中没看到”判为通过。未完成时保留原有部分成果，并给出未核对项。

## 不应夸大的边界

- 这是 Agent 原生调用路径的策略控制，不是操作系统沙箱；不能承诺抵御已在宿主机任意执行代码的恶意进程或任意并发文件系统攻击。自动后台服务、用户自己打开的应用不属于“模型启动工具”的执行轨迹。
- 不对通用脚本/MCP 做关键词扫描后冒充安全。带操作禁令时这些能力会被保守阻止；例如依赖 Python/Node 的 PPT 生成流程可能因此停下。隔离运行后再开放属于后续阶段，不可报告为现在已具备。
- 目前使用结构化规则提取，不是完整自然语言语义审查。未实现的操作约束要求明确范围；业务语义依赖具名测试，但测试自身是否充分仍属阶段 5。
- 文件哈希检查当前限制为工作区内、普通文件、2 MiB 以内；不存在/不可读/过大/目录/链接等都不能伪装为人工验收通过。没有可核对的交付文件时会保留未验收状态。
- “必须先人工确认再修改”的前置约束不会偷换成事后确认；尚无对应安全执行流程时拒绝修改并要求明确下一步。非本地交互来源没有本轮人工验收通道，不自动批准。
- 运行中 steering、跨重启完整轨迹复用、权限变更版本管理仍属于阶段 3；当前恢复缺轨迹时保守不通过，不声称已经实现完整连续性。
- 模型版本、付费预算等阶段 0 剩余信息仍未提供。没有真实模型前后成绩，不给一次完成率/费用收益或竞品分数。
