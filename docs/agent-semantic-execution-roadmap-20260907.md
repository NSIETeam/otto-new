## 1. 结论与当前差距

目标不是复制某个 Agent 的措辞，而是减少漏要求、错误交付、重复失败、方向变更后继续旧操作，以及用户不得不补救的次数。采用三个层次：

- 原生规则负责可确定验证的边界、授权、版本、执行回执和交付条件。
- 模型负责语义拆解、替代方案、证据解释和表达；模型的自报不直接成为验证成功。
- 独立任务评分、真实模型运行和必要的人审验证实际收益；代码结构不能推出竞品分数。

用户提供的十分制分数暂不作为基线。相同模型、工具、预算和任务条件下未做对照前，不量化宣称与 Codex/Grok 的差距。

## 2. 架构原则与共用数据

### 一份权威任务状态

扩展现有 `TaskContractLedger`、`TaskGraphCoordinator` 和 `FileTurnRecoveryStore`，不另起第二套 Agent Loop 或平行任务状态库。需求是原始依据，任务图是执行投影，证据是可追溯观察，压缩文本只是供模型读取的视图。

拟扩展的数据关系：

`用户消息及版本 → 需求/约束 → 目标与验收项 → 执行与证据 → 交付结论`

共享标识至少包括 task/turn、requestRevision、requirementId、objectiveId、criterionId、toolCallId、artifact/source version、policy revision。重复消息和回执按 ID 去重。过时回执保留审计，但不能用于当前完成判定。

需求采用以下用户概念，内部保留更细类型：

- 必须实现：目标结果。
- 必须保持：既有行为、兼容性和数据完整性。
- 禁止发生：禁止的执行副作用或输出内容。
- 人工判断：需要真实人员作出的验收或决策。

人工判断在内部作为验收方式，与需求类型正交；例如视觉质量可以要求人工确认，但不是模型增加一个 manual 标签就能豁免。范围限制、前置条件单独记录，不强行塞进负向字符串。

### 职责与信任边界

- Core：共享纯类型、执行生命周期、统一权限门、事件/检查点接口、压缩协调。不得导入 Server 或 Electron 业务模块。
- Server：在既有运行时及可替换领域组件中编排任务合同、证据、策略与持久恢复。不要继续把所有算法堆入 runtime.ts。
- Desktop：进展、最终答案、产物预览和真实用户确认；不独立计算任务是否完成。
- 工具适配器：报告可信的执行状态、读写对象、来源和产物。未知 MCP 元数据是声明，不直接取得信任。
- Evals：独立评分与隔离环境，不调用产品自身的 completed 布尔值作为唯一判据。

工具权限始终来自现有政策和真实用户授权；模型计划、审查模型意见和网页文字都不能扩大权限。源码和网页中出现的命令不能被当成用户新指令。

## 3. 实施顺序

顺序：阶段 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7。

评测从阶段 0 贯穿全部阶段。阶段 7 是完整对照及发布门槛，不是到最后才开始测。每阶段拆成可单独评审和回滚的“小协议/回归测试”“实现”“端到端验证”改动。

### 阶段 0：冻结基线和验收协议

解决问题：10；为所有阶段提供可比较结果。

实施：

1. 在隔离工作区固定当前参与交付的源码，包括相关未提交内容，记录路径/哈希、锁文件、工具及运行环境。不能只记录 HEAD，也不能把凭据、用户材料或无关修改一起打包。
2. 先登记下面的关键反例及独立评分规则，再改实现；冻结开发集与未参与调优的留出集。
3. 沿用现有 live harness，保留同模型、端点、参数、工具版本、任务、评分器和费用口径的可比性检查。补录 adaptiveExecution、压缩及 UI 等本次实际变更模块的内容哈希。
4. 未确定模型凭据与费用上限时，只运行确定性测试并保留可重跑的旧版；不能把模拟模型分数标成真实效果。

验收：旧版能在隔离环境重复启动；每次结果能追溯精确源码；缺失用量记为未知而非 0；当前失败案例不因新评分器变宽而消失。

首轮最小对照从 8 个代表任务开始，不为凑齐大样本阻塞安全漏洞修复。后续按固定评分器回跑旧版。

### 阶段 1：需求与禁止行为成为运行约束

解决问题：1，并为 4、6、7 打基础。业务修复第一优先级。

实施：

1. 复用现有否定约束提取，补 source message ID、原文范围、作用对象、版本、优先级及明确替代关系。稳定 ID 不跟随列表顺序变化。
2. 对受支持的约束生成原生监控项：禁止打开外部应用、禁止部署/发送、限定写入范围、禁止在可见正文暴露本地路径等。
3. 执行前门控和输出前门控共同执行；不能仅在最后发现 WPS 已打开。shell/脚本/间接 MCP 同样受权限及隔离策略限制。无法可靠判定副作用的调用不能声明符合禁止要求。
4. 负向证明必须限定任务、作用域和观察区间，且有完整事件覆盖。没有日志不等于没有发生。观察断档记 unknown，不能自动通过。
5. 产品回归中的负向测试与当前任务的执行轨迹证明分开记录。一个名为 must_not_happen 的测试通过，不代表本次运行从未违规。
6. 人工验收接入真实确认回执：绑定账号、验收项、当前产物/需求版本；模型不能伪造。版本改变后，旧确认失效。

PPT 示例的验收：有效 PPT、应用内可点击链接；受监控区间没有外部打开调用；最终渲染正文无裸绝对路径。链接应优先使用产物 ID，不把友好链接误删成不可点击文本。已发生禁止动作不能靠最后修改措辞清除违规记录。

重点反例：混合肯定/否定、表格同词不同模块、英文否定、双重否定、引用中的指令、默认保留与明确撤销、脚本间接启动 WPS、缺失事件、伪造人工确认。

主要落点：taskRequirements、taskContract、协议、runtime/Core 政策钩子、Desktop 外部打开与输出呈现边界。

放行条件：关键禁止行为测试集中实际执行数为 0；观察不完整无法报“已验证”；普通问答不被强制要求测试命令。

### 阶段 2：收紧完成判定和即时失败门控

解决问题：2、4 的确定性部分，以及当前 3 的已知漏洞。

实施：

1. 把“做过动作”和“满足要求”分开。产物按 requirement/criterion 对齐，不再以任意一个 verified 文件代表全部要求。
2. 产物验证分层：实际对象存在且非空 → 可解析的完整格式 → 内容要求 → 请求所需的渲染/交互检查。现有 magic/header 检查只是第一层筛选；Office 压缩包需检查结构、关系及内容，设置解压与内存上限。
3. 证据绑定当前文件内容哈希/版本；验证后再修改即使文件长度相同也要失效。修复一个文件只使受影响证据失效，不要求无关工作重跑。
4. 测试证据保留命令、目录、用例 ID、正常/异常/边界场景及真实过程回执；截断、skip、伪造 stdout 和只有退出码不能冒充覆盖。
5. 当前运行中每个工具完成立即登记失败，后续未开始调用重新过门；相同并行读合并或共享结果。已启动的并行操作不能被宣称已撤回。
6. 失败限制按目标和原因解除；无关成功不得解除。恢复节点绑定原失败及对应修复/复验，不能被任意成功读操作关闭。
7. 完成状态只有单一提交点，消费最新版合同和有效证据；保留部分成果及剩余问题。非空正文只是存在性检查，不代表回答正确；普通问答不需要凭空造工具证据。

重点反例：要求 PPT+PDF 只生成其一、损坏 PPT 包、空白幻灯片、旧文件冒充新产物、修改后旧验证、假工具名、同批重复失败、无关成功解锁、缺项却 markDelivered、未完成时文件链接丢失。

主要落点：agentTurnTracker、verificationEvidence、testCaseEvidence、taskContract、taskGraph、adaptiveExecution、runtime 和领域产物检查器。

放行条件：上述反例均不能错误完成；真实完成路径能正常交付；新增门控不会制造无限重试或把所有研究/普通回答一律拦住。

### 阶段 3：实时纠偏、压缩和恢复共用版本化状态

解决问题：6、7。

实施：

1. 新增明确 steering 协议，区分补充、替换、撤销、暂停、下一轮；不悄悄改变旧客户端 merge 的语义。客户端和服务端协商能力。
2. 持久记录收到消息、已应用版本和应答。相同 clientMessageId 不重复应用；“收到”不等于“生效”。
3. 用户撤回范围时先建立调度栅栏，再在安全点更新合同和剩余任务图；工具调用真正启动前再次检查版本，过期批准不能放行旧任务。
4. 只取消未开始节点；可取消的在途工具尽力取消，未知结果进入核对。外部写入在核对前不重放、不自动换渠道补发。
5. 已完成且仍适用的证据继承；受目标变更影响的节点失效。恢复用户文件须依赖原始快照和当前差异核对，不能覆盖同时发生的人工修改。
6. 压缩只生成权威账本的有界视图。硬约束和未完成 ID 完整持久保存；模型上下文按需加载。超过视图上限时分页/摘要，不静默丢弃有效限制。
7. 明确同级用户授权可按范围取代旧要求，但不能降低系统/企业政策；含混冲突保守暂停相关操作，询问必要问题，其余独立工作可继续。

重点反例：审批等待时撤回、同批第二个写入前纠偏、模型流式时追加、重复投递、断线后 ACK 重发、压缩超过 12 条约束、部分替换不取消全部任务、重启后不重复外部发送。

主要落点：server、runtime、sessions、turnRecoveryStore、taskContract、compressionInvariants、Core 生命周期接口、Desktop 输入协议。

放行条件：已应用纠偏后无旧版本新写入；关键约束无静默丢失；在途副作用被如实记录；单次已授权外部行为不因重启自动重复。

### 阶段 4：受控策略选择与局部修复复验

解决问题：3、8。

实施：

1. 错误优先使用原生类型、HTTP/进程/资源状态，正则仅作为兼容兜底。按目标、前置条件和环境版本保存失败记忆。
2. 必要时生成至多 2–3 个候选策略；普通瞬时只读错误走有限退避，不为每个小错误再增加多次模型调用。
3. 候选必须说明可观察失败原因、改变的关键步骤、所需能力/权限、原验收覆盖、证据获取方式、预估费用/耗时和回退点；不保存或要求展示隐藏推理过程。
4. 原生层先排除越权、降标、同义参数重试、能力缺失和超预算方案，再按风险/代价及历史结果选择；若只剩不安全方案，保留成果并明确阻碍。
5. 扩大局部修复到授权工作区内、与已失败验收有因果关系的文件及新增测试。允许多文件补丁和固定参数的受限格式化工具；基于文件数/字节/修复轮次/耗时预算，而非一律“两次写入”。
6. 新增文件、配置和 Schema 仍需对应原需求和权限；生产迁移、安装执行外部依赖、提交发布、发送消息不因“自动收尾”获得许可。
7. 修复后重新检查受影响项目，失败后比较策略而非机械重试。局部回退只恢复本任务仍拥有的改动；外部动作不存在通用撤销。

重点反例：改 timeout 冒充新策略、错误测试命令替代、新增测试后修复、跨文件修复、用户同时改文件、无关写入解锁、超预算、外部发送超时后换工具补发。

主要落点：adaptiveExecution、deliveryRepair、deliveryClosure、taskContract、taskGraph、runtime 和既有预算/政策接口。

放行条件：原验收不被降低；失败记忆重启后仍有效；验证确实绑定修复目标；本地修复成功率及无效重复次数优于固定旧版，且无权限回归。

### 阶段 5：结论—证据关系和语义审查

解决问题：4 的语义部分、5，并深化 2。

实施：

1. 引用状态拆分为发现、取得原文、存在定位、支持结论、存在争议，不能继续用一个 verified 表示全部。
2. 每个重要 claim 记录原文位置、来源作者/机构、发布/更新/事实发生日期、取回时间、版本/哈希、证据摘录、适用条件。来源是否一手由声明的事实领域决定，不以“官网域名”一刀切。
3. 区分直接事实、计算结果和推断。数字记录数值、单位、币种、期间和口径；计算结果记录公式及输入来源，原生复算。
4. 原文证据可精确定位，不自动意味着蕴含成立。模型/规则交叉检查证据是否支持主张；相反证据作为 contradicts 关系保留，重要冲突不悄悄取一边。
5. 任务计划审查读取原始用户要求和证据，不只读执行模型的自评；检查漏项、弱测试和未验证假设。审查可以发现风险，不能保证所有隐含语义都正确。
6. 原生静态审查优先；对复杂/高风险任务按预算追加独立审查调用。模型评分与人类样本校准；没有校准的数据不输出精确“可信度百分比”。
7. 外部网页、附件和企业知识都按不可信内容处理；证据摘录最小化、受权限及保留期约束，不因审查上传更多企业敏感内容。

重点反例：正确 URL 错误数字、万元/亿元混淆、自然年/财年错配、旧页面回答最新状态、搜索摘要冒充已读全文、新闻转述冒充原始来源、两份有效来源矛盾、模型虚构段落、测试名称匹配但断言无效。

主要落点：agentTurnTracker 的引用边界、taskContract 语义审查接口、Server 证据领域组件、来源适配器、Evals 事实评分器。

放行条件：重要主张能定位支持证据；不足显示未知或有条件推断；不以链接数量证明正确；独立留出样本的事实/验收质量改善得到报告支持。

### 阶段 6：自然输出与轻重路径优化

解决问题：9，以及不必要的模型调用和等待。

实施：

1. finalSections 改为可选表达建议，按用户要答案、决策、产物还是详细审计选择内容，不固定打印所有栏目。
2. 普通短问题直接回答；改代码通常交付结果及必要验证；产物优先显示友好链接/预览；限制只在影响使用或结果可信度时说明，关键风险不能被隐藏。
3. 模型生成结构化的用户可见进展候选和最终内容，运行时绑定发现/证据/阻碍；保留重要发现，合并重复说明。不要用一个未经校准的“重要性分数”自动永久删除历史。
4. ChatView 负责呈现和兼容旧记录，不猜测哪条工具输出是最终答案。不展示“直接回答/并行读取/计划执行”等内部路由标签。
5. 低风险回答可流式；需要交付验收的断言先通过门控。有意义的已验证进展可以提前展示，不能所有文本都压到最终才出现。
6. 简单任务零额外审查模型调用；复杂任务用输入/状态版本缓存审查，按预算触发重规划，减少重复指令和上下文重发。

重点反例：一句话问题变验收报告、等待只有泛化状态、重要中间发现被覆盖、每个工具结果都有复制/重试按钮、未验证完成断言先流出、PPT 裸路径、未经请求打开外部程序。

主要落点：turnControlPolicy、runtime 输出事件、Core 提示组装、ChatView/Message 和产物呈现；保留 Otto 的企业/园区视觉和功能。

放行条件：简单问题不新增整套检查链；关键发现和限制不丢失；用户盲评更清楚而非仅“更短”；首次有用反馈及总耗时不显著退化。

### 阶段 7：固定模型真实对照及灰度放行

解决问题：10；验收整个闭环，不新增架构大改。

任务集建议：8 类各 4 项，共 32 项；24 项开发集、8 项留出集。每版每项 3 次，两版共 192 次，分批执行，每批保持既有最多 24 次及更严格费用/时间上限。数量是计划，不是已经执行。

任务类别：

1. 普通问答与简短指令，检查是否过度规划。
2. 带日期、数字、一手来源和矛盾证据的研究。
3. 隔离真实代码库的缺陷修复，使用独立隐藏业务测试。
4. PPT/PDF/表格文件交付，真实解析和可用渲染检查。
5. 测试应用 GUI 操作与重启恢复，不接管用户生产工作窗口。
6. 运行中撤销、目标替换、多轮长任务压缩。
7. 本地测试企业工单/消息流程，使用合成账号和受控副作用接收端。
8. 网络/工具故障、重规划、恢复和重复提交防护。

评分口径：

- 一次完成率：一次用户委托后，在固定预算内满足独立验收且无需纠错性补充；允许内部合理修复。必要澄清和用户主动变更另计。
- 错误交付率：独立验收失败但对用户声称完成的比例；同时披露未完成率，防止靠拒绝全部任务刷低该指标。
- 约束违反率：已执行的禁止动作、越界写入和可见输出违规；受阻的违规尝试另记。
- 用户负担：非必要催促、纠错和手工补救次数，区分必要审批。
- 恢复质量：有效证据继承、无效重复工具调用、外部副作用重复、方向变更生效延迟。
- 事实质量：关键主张证据覆盖、数字一致性、过期来源和未披露矛盾，由独立评分器与人审抽样核查。
- 性能成本：首次有用反馈、端到端耗时 p50/p95、tokens、工具费用、模型费用和内存。缺失费用不填零。

对照要求：同模型固定版本、同权限/依赖/工具和评分器、同任务快照、同预算；新旧版交错运行，避免时间段偏差。冻结网页证据任务用于可比性，实时联网任务另组汇报。重试/超时/失败全部入分母，不能只展示成功样本。

人审采用匿名随机顺序，核查评分器偏差；报告配对差异、区间和分组样本量。小样本只能说明趋势，不能据此宣布达到竞品水平。比较整个产品时另控制模型差异，不把模型升级收益算成运行时收益。

发布门槛：关键安全/丢消息/重复副作用/错误完成反例在测试集中零失败；核心任务无新重大回归；真实完成率和用户负担有可解释改善；性能与费用满足预先约定上限。门槛在看新结果前锁定，不能事后改分母。

## 4. 回滚、兼容与工作拆分

- 每阶段独立开关、协议版本和迁移测试；先隔离回放，再在获准的测试企业内灰度，再单独批准生产部署。
- “影子模式”只比较判定，不把新策略实际执行两遍；安全约束仍由当前有效政策执行。
- 账本采用兼容性新增，保留旧记录。旧客户端不能理解的批准/纠偏请求明确提示能力不足，不静默当作成功。
- 关闭新能力不等于解除用户禁止项。若回滚后的引擎无法解释新账本，应停止受影响任务并提示升级/核对，不能带着丢失的约束继续执行。
- 回滚代码与回滚用户数据分开；不自动逆向生产迁移，不重放外部写入，不用 reset/整目录覆盖恢复用户工作区。
- 先固定共享协议及测试夹具，再拆分产物检查、来源证据、UI 呈现与评测等独立改动；同一时段避免多个实现者同时修改 runtime/taskContract 状态主线。
- 延续仓库验证顺序：doctor、差异检查、定向测试、类型检查，再做必要的包级/集成/界面验证。更新跨包协议和执行边界时同步 code-map/boundary。
- 不新增独立图数据库或重型框架作为先决条件；先用现有存储与结构化关系，真实规模证明需要后再引入。

阶段 0 的最小源码身份与关键反例登记，加阶段 1 的“禁止外部打开/裸路径输出”纵向闭环：

2. 将真实调用门和输出验证与当前约束版本绑定，不改园区、招聘和企业记忆业务。
