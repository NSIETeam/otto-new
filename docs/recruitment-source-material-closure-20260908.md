## 具体入口

1. 智能招聘中填写岗位目标，连接企业已授权来源。
2. 打开“候选人来源”，执行“按当前岗位自动寻才”。
3. 确认已取得本批候选人材料分析与限期保存授权。
4. 在来源结果上点击“获取材料并分析”，或者在对话说“分析找到的第 1 位候选人”。多个来源对应同一候选人时，通过右侧明确选择材料来源。
5. 查看来源正文与历史版本，继续说“生成面试问题”。

新搜索从第一页开始，不复用其他岗位的后台同步游标。界面明确提示仍有后续分页或部分来源失败，不把当前一批结果当成全部人才库。

## 服务端与连接器契约

新增受保护接口 `POST /enterprise/recruitment/sources/material`，能力标记 `recruitment_source_material_v1`。

请求只包括 `runId`、`requisitionId`、`canonicalId`、`sourceId`。企业和账号从当前登录会话获取。服务端要求候选人属于该账号、该岗位的已存检索记录，检索有效期为 24 小时；读取前后都重新检查来源授权。

`RecruitmentSourceAdapter.getCandidate` 返回以下数据，而不是把一个简历 URL 交给渲染进程下载：

```json
{
  "sourceRecordId": "平台候选人记录编号",
  "fileName": "resume.txt",
  "text": "经过连接器提取的原始正文",
  "completeness": "full_text"
}
```

`completeness` 可以为 `full_text`、`partial`、`unavailable`。没有明确声明完整性的非空文字按部分资料处理；空文字按无正文处理。正文上限为 80,000 个 UTF-16 字符，超限明确报错，不截断后冒充完整正文。

通用 MCP 适配器调用已审核的 `get_candidate`，支持直接 JSON、MCP `structuredContent` 和文本 JSON 包装。不调用消息发送、发布职位或安排面试工具。具体平台需要独立适配其官方工具名与字段，通用契约不是 Workable/Ashby 的原生接口格式。

来源运行时提供 `materialReadable`，与“可以检索”分开显示。只有返回值为真时，右侧才允许读取材料。连接器错误采用固定错误信息，材料审计钩子只接收编号、哈希和完整性，不包含简历正文。

## 仍未完成，不得宣称已上线

- 没有取得 Workable、Ashby 或其他招聘平台的正式企业授权，也没有完成真实平台端到端验收。
- 现有生产启动流程仍需由部署方注入正式来源运行时及连接器；不能仅配置一个平台名称就自动搜人。
- 当前候选人正文、分析和历史版本仍保存在客户端内存工作区。关闭应用不会作为共享档案持久保存。服务端现有的持久存储是检索记录，不等于完整候选人共享档案。
- 读取来源仍沿用管理员边界；HR/用人负责人岗位级权限尚未实现。
- 不同岗位的来源导入分别保留记录，但没有宣称已完成“一个候选人关联多个岗位”的服务端人物实体与投递实体拆分。
- 尚未实现邮箱收件、候选人投递页、员工推荐、正式后台调度、消息发送及双向阶段同步。
- 当前限制为每工作区最多 100 位来源导入候选人、每人最多 20 个历史版本；不是已经完成大规模生产压力验收。
