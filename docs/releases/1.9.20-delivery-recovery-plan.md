不重跑失败 job、不改生产审批或临时配置凭据。

## 本轮交付机制修复

1. `rollback-enterprise` 的首次恢复、重复确认分支，将健康检查输出定向到 stderr。
   stdout 仍必须只有原有精确回执；健康检查失败不能写成功回执。
2. root 网关增加受同一账号、锁、角色、大小、摘要与目录边界控制的 `upload-status`。
   `upload-file ... OFFSET` 可从 root-only 的未接收前缀继续；旧的无 OFFSET 调用保持兼容。
3. 客户端必须比较服务器前缀 SHA-256 与锁定本地文件的同长度前缀，并重新检查整个本地文件身份。
   服务端重新读前缀，完整大小及 SHA-256 通过后才原子改名为已接收文件。
4. 单次操作仍限制 1800 秒；客户端最多 3 次尝试；原 workflow 的 90 分钟 job 上限不变。
   断线、超时、丢回执可恢复，错误身份和不精确的成功回执不能以重试绕过。
   每次起点及每 30 秒进度走 stderr；公开清单不引用 partial 文件。
5. 前缀计入事务配额，仍保留 staging 副本和磁盘余量；拒绝符号链接、硬链接、错误 owner/mode、
   过期偏移、尾随字节与完整摘要不符。原签名验证和镜像原子发布机制不变。
   同一固定文件目标只允许一个未完成身份，不能用不同 SHA 堆积零长度前缀。

1800 秒不再意味着丢掉已传字节，但本修复不能使慢链路凭空变快。
真实吞吐和整个 staging 预计时间必须测量，不能把模拟断线测试写成公网速度验收。

## 恢复的执行顺序

### A. 先完成只读闭环与新机制 CI

- 修复通过 PR 的 Linux root 事务、脚本、lint 及现有发布安全合同。
- 原运行状态、补偿记录、两仓 Release ID、tag commit、正文摘要、完整 16 件资产向量、
  两仓 latest、新旧镜像和服务器当前身份做一次新快照。
- 由固定 root 网关核实原企业事务的耐久回滚回执及私有部署健康，不能仅使用公开 health。
- 如需更新固定 root 网关，必须使用审计后的源码、备份、原子安装与失败恢复，并验证
  网关/helper SHA-256、固定配置路径、两套隔离账号/密钥及 Ed25519 trust anchor。
  不执行任意包脚本、不临时开放通用 sudo。

### B. 单独建立“原成品恢复”审批与意图

当前 `release.yml` 和发布规范禁止复用失败版本及 Re-run jobs。
因此不能拿修复后的普通发布流水线直接重跑 `v1.9.20`。
要保留原成品，必须另行批准并实现一次受约束的恢复事务；**本文件没有实现或授权该事务**。

恢复意图至少绑定：原 run/attempt、两仓原 Release ID、原成品源码及全部原始资产摘要、
当前补偿后的 latest 快照、新恢复 run/attempt、单独的交付机制源码与摘要、
生产基线身份、固定操作集合和授权例外。成品源码与机制源码不能互相冒充。
审批仍由保护环境管理。临时自批、凭据使用及删除需要新的明确授权，不沿用已消费的单次授权。

### C. 先备齐原字节，再切生产

- 匿名下载正式仓原件，校验 16 件完整向量、签名摘要、对应源码旁车及成品来源。
- 镜像 `latest.json` 必须来自原运行的镜像 artifact，并匹配原
  `UPDATE-MIRROR-SHA256SUMS` 与 Ed25519 签名；GitHub 资产中的 `latest.json`
  不能直接冒充镜像清单。原镜像 artifact 不可获得或摘要不一致即停止。
- 测量有界传输并提前 staging 六件桌面文件及清单/签名。生产继续运行 `1.9.18`，
  不因为正在传文件而先切换企业服务或更新 latest。
- 原失败事务若仍有目录，先证明运行终止、核对原事务，再按精确事务号清理。
  不用新事务绕过未完成账本；任何前缀只有证明与同一锁定文件一致才可恢复。
- staging 全量通过签名、大小、摘要及足够时间预算后，才允许进入短生产切换窗口。

### D. 受保护切换与补偿

重新执行原签名企业包的隔离数据库 canary、备份、升级及精确私有/公网验收；
这些步骤不能因原运行曾通过而跳过。旧账号、加密历史、设备连续性和业务回归必须记录范围。

随后按固定事务公开镜像、复核匿名下载、新旧更新入口，再完成兼容仓既有草稿公开及
两仓 latest 提升。仅允许既有 Release 的合法公开/指针操作，不改 tag、正文或资产字节，
不删除并重建同名资产。

若镜像历史表已经烧毁 `1.9.20` 或原事务无法安全恢复，则停止，不能删除账本或
修改失败运行来强行复用版本。必须另行设计并审计严格的同字节恢复接口；若不能证明安全，
就明确告知原成品补发不可执行，不偷偷新打包。

失败时仍先补偿镜像和两仓 latest，再按锁定企业身份恢复并核对精确耐久回执。
有业务新写入时必须按现有回滚规范处理，不能用旧数据库覆盖新数据。
最后所有 job 完成，才清理本次明确授权的临时凭据并核对审批恢复。
